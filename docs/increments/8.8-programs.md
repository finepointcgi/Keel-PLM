## Assumptions (FEAT-PRG-n; not added to assumptions.md)
- FEAT-PRG-1: The program code is the program marking code. A program's markings must name its own code (database CHECK), so the page is readable by members only. Membership is the identity provider's; the module never writes it.
  A creator must be allowed to modify an object with those markings; a manager or owner who could not read the program or item is refused. No program page, item or deliverable creation or edit grants or widens access.
- FEAT-PRG-2: Programs are never deleted (status Cancelled or Complete). A closed program (Complete, Cancelled) takes no schedule changes until its status is changed.
- FEAT-PRG-3: Items (phase, milestone, task) carry their own markings, covering the program's; they are never deleted (status Cancelled). Dependencies join tasks and milestones only (finish to start, lag from -365 to 365 days).
  A milestone is one day. Calendar days only: there are no working calendars.
- FEAT-PRG-4: A reader who cannot read an item sees a placeholder with its position and planned dates and nothing else, in the table and in the chart; placeholders are in no count, percentage, critical path or dependency.
  The schedule is computed on the items and links the reader can read; a link through a hidden item is not drawn, so a reader's critical path can differ from a wider reader's.
- FEAT-PRG-5: Critical path method with a status date: completed items are fixed at actual dates; started items keep their actual start and finish no earlier than the status date; items not started start no earlier than the status date;
  planned start is a no-earlier-than constraint; float is late start minus early start and an open item with no float is critical. Percent complete rolls up by duration (at least one day) and ignores cancelled items.
- FEAT-PRG-6: Deliverable readiness maps the lifecycle state label of the target (Released, Approved, Established, Closed, Implemented, Resolved, Dispositioned = ready; Under review, MRB review, Verification, Awaiting customer, Evaluating = in review;
  Obsolete, Superseded, Archived, Cancelled, Rejected, Withdrawn, Revoked, Expired = ended; anything else in work). A target the reader cannot read or that does not exist is "not visible to you". A deliverable is overdue when its due date has passed and it is not ready.
- FEAT-PRG-7: Baselines freeze planned start and end of every item that is not cancelled (ids and dates only) and are immutable (triggers). Slip is the planned end minus the baseline end for readable items, and the forecast end minus the planned end for the forecast.
  Moving an end later needs a reason, and every date move is written to an immutable log.
- FEAT-PRG-8: A gate review is a milestone with a gate type and a number (GR-nnnnnn). It needs at least one criterion and every required criterion met or not applicable before it can be submitted. Submitting freezes the checklist and the gate; approval needs all chosen
  approvers (template `gate-review-approval`, replaceable by administrators) and completes the milestone; the database refuses Approved without an approving signature. A gate cannot be completed by hand. Cancelling or rejecting the review returns it to Draft; each submission has its own snapshot.
- FEAT-PRG-9: `program.milestone_reached` is emitted when a gate review is approved and when a milestone (not a task) is completed by hand, once per completion, with the markings of the milestone; the payload names the program code, milestone key and name, gate type and number, planned and actual dates.
- FEAT-PRG-10: Milestone due soon (default 7 days, `Keel:Programs:DueWarningDays`) and overdue notices go once per milestone to its owner as pointer-only system notices (kind, program code, opaque id), only if the owner may read the milestone; a job runs every 15 minutes (`Keel:Programs:MaintenanceEnabled`, `MaintenanceInterval`).
- FEAT-PRG-11: Audit events carry keys, numbers, states and counts only; a slip reason is kept in the schedule log, not in the audit event. Read events (program, schedule, dashboard, deliverables, gate, my work) are audited like other module reads.
- FEAT-PRG-12: `program` and `gate` are awareness kinds (watch, comments, activity). Recent items and favorites support `program`; saved searches do not. Search prefix `pg:`; palette "Go to Programs".
- FEAT-PRG-13: Deliverable targets are looked up through `IObjectAccess` (a key lookup that makes no decision) and the policy on the target's markings for the reader, because the owning modules' search paths are not reachable from a module (architecture rule). The lookup never writes and the program stores no target data.

## Not built / not verified
- Resource loading, cost, working calendars, lead and lag types other than finish to start, drag editing in the chart, program-level approval of the baseline (a baseline is taken by anyone who may modify the program), per-person notification preferences beyond the standard kinds.
- Comments and watch on individual items; the program carries them. Items have no activity feed of their own beyond the program's.
- ERP sinks receive `program.milestone_reached` only if their clearance allows the milestone's markings (the standard outbound release check); no consumer exists yet.
