It closes the follow-ups listed in the status of [docs/CLAUDE.md](../CLAUDE.md): the `mbom.released` ERP event, classification and effectivity in the migration importer, and the demo seed. 5. **Small fixes.** The shared start-review dialog names the object ("The MBOM is locked ...") from the workflow template's object type (one razor file). No new configuration setting was added (`docs/ops/configuration.md` is unchanged; the migration options are mapping-file members).

## Assumptions and decisions (FUP-n)
| # | Decision |
|---|---|
| FUP-1 | `mbom.released` follows `bom.published`: event markings are the MBOM's own; a line whose child part the MBOM's markings do not cover is a `restricted` placeholder (find number, alternate, quantity, unit) and its EBOM links and child-MBOM reference are not named; an MBOM line has no subtree, so there is nothing further to omit; a sink whose profile does not clear the markings withholds the event. A Make child's released MBOM of the same plant is named (`childMbom`) only when the MBOM's markings cover that MBOM too. The pull endpoint takes the **part** number plus the plant (an MBOM is per part and plant) and returns the same redaction as the in-app read. Version 1; `aggregate.type` is `mbom`. |
| FUP-2 | Classification. Source classes are item-level but class data is iteration-owned, so the class goes onto **every imported iteration** (`scope: allIterations`, default) or only the last one. Existing Keel classes are never changed by an import; a different parent or attribute type is an error, other differences are warnings, a retired class (in Keel or staged) cannot receive parts. Classes the source hierarchy has and Keel lacks are created when `createMissingClasses` (default true); a staged class with status retired is not created. The hierarchy travels as `classification.json` (package hash covered). `classification.load` and `effectivity.load` default to **false** (the previous behaviour is kept unless the mapping opts in). One class per part (ADM-10). |
| FUP-3 | Effectivity. Line effectivity only. Revision-level effectivity (what a change notice gives a released revision) is not specified by any supported source: `effectivity.revisionLevel: true` throws `NotSupportedException` naming FUP-3 (CLI exit code 6). One Keel line per range; alternates share the find number and must not overlap; contexts are never created by an import (a mapped context must exist in Keel); dates are UTC days (offsets are converted; the end day is inclusive: an assumption to confirm with real exports); lot ordinals come from block names (mapping blocks plus the context's blocks). PLM XML uses `effectivityRefs` on `ProductInstance` and `LotEffectivity` with `start`/`end` as assumed conventions (the public schema documents the three types and their attributes, not their use on instances). |
| FUP-4 | Seed. Classification happens inside the check-out that already links documents or carries structure (class data is iteration-owned, so it must precede the release). The seed registers the same modules as the API host: the outbox sink (events accumulate; no dispatcher, no webhook sink), the classification participant, TDP sources and a throwaway signing key and file-drop root in a temp directory that is deleted at the end. The pod MBOM is generated from its latest EBOM (the pod is In Work) and its EBOM then changes; the **drive module** MBOM is the one released (a sub-assembly without Make assemblies below it, which would block release). The release baseline is of the pressure housing: the pod itself is not Released. Part numbers, document numbers and ECN-000001 to ECN-000003 are unchanged; the new ECN is ECN-000004. |
| FUP-5 | Both executables (`keel-import`, `keel-seed`) now have an explicit entry point instead of top-level statements: once they reference `Keel.Admin` (ASP.NET Core framework reference) their `Program` type became visible next to the API host's `Program` and broke the integration test project. |

* Date effectivity is loaded and reconciled, but the as-of sampling is for serials only.

* The seeded TDP record cannot be verified against a site key (it was signed with a key that existed only during the seed).
* The E2E suite (`KEEL_E2E=1`, 25 tests) passes: the demo counts the tests read (63 parts, 12 documents, 8 changes) did not change. Two tests were adapted to the richer seed: the MBOM test generates for the gimbal assembly (the pod and the drive module now have seeded MBOMs) and the classification test picks its own "Fasteners" class by code (the seeded tree has one too).
