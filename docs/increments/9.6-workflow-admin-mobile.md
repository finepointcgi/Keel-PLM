# 9.6 Workflow designer and phone approvals (2026-10-30)

Migration 0035, ADR-0056, assumptions A82-A84.

## Delivered
| Area | What |
|---|---|
| Steps editor | Workflow templates page: list with running reviews per version, **New workflow**, **Copy**, ordered steps (person, several people with All / Any / N of them, anyone holding a role), review or approval, due days, the signature meanings of the step read from the engine, move up/down, add, remove. Templates that are not a plain list of steps open in Advanced nodes or JSON with the reason. |
| Validate, preview, publish | Validate and publish are the engine's parser and the existing audited upload. **Preview** draws the definition with the existing workflow map (`WorkflowService.PreviewTemplateMapAsync`, nothing stored). |
| Drafts | `wf.template_draft` (migration 0035), `IWorkflowTemplateAdmin.ListDraftsAsync / SaveDraftAsync / DiscardDraftAsync`; publish removes the draft in the same transaction. Audit: `admin.workflow_draft_save`, `admin.workflow_draft_discard`, denials `admin.workflow_drafts_list`, `admin.workflow_meanings_list`, `admin.workflow_preview`; `draftRemoved` on `workflow.template_upload`. All under the catalog's `admin.` hidden prefix. |
| Versions | Unchanged mechanism (an instance copies its definition and version at start); now visible (running reviews per version, count in the publish confirmation) and covered by a test that publishes version 2 under a running version 1. |
| Phone approvals | `/approve` (cards) and `/approve/{id}` (review summary: item, revision, version, state, markings chip and banners, submitter's note, description, attributes, the SHA-256 content hash the signature records, progress map folded away; comment; full-width 56 px decision buttons). `SignPanel` has a `Phone` layout. Same `SignAsync`, so step-up, separation of duties and audit are unchanged; step-up returns to `/approve/{id}` with the comment kept. My tasks links to the phone view. |
| Engine additions | `ReviewSummary` on `TaskDetail` (content hash, submitter's note, template name and version), `MapTask.SlotLabel` and the preview mode of `WorkflowMapBuilder`, `TemplateVersionInfo.RunningReviews`, `SignatureMeaning` list. |

## Tests
- Unit (`WorkflowStepsTests`, 19): seeded template round-trips through the steps view; everything the steps view writes is accepted by `TemplateParser`; new step ids; five shapes that fall back to the advanced views; preview map builder and the live map unchanged; map label; phone `SignPanel`; every new audit action is classified.
- Integration (`WorkflowAdminMobileTests`, 11, real Postgres): draft save, replace, list, discard and audit; refusals and audited denials; publish deletes the draft atomically and a refused publish keeps it; signature meanings from the reason codes; a running review keeps version 1 while version 2 is published and later reviews use version 2; preview map; preview refuses an invalid definition with the engine's message; a three-step workflow written by the steps editor is published and run to release (person, 2-of-2 group, role pool); the summary hash equals the stored signature hash; running-review counts honour the read filter (an administrator off program ORCA sees 0); a reader who lost access gets no summary, hash or item name (checked on the serialized result) and the denial is audited.
- E2E (`WorkflowAdminMobileE2ETests`, 2): the designer end to end (new, rename, add and move with the keyboard, validate, preview, save a draft, reload, continue, publish, pin, axe at 1280 and 375 px, no sideways scroll); two approvers on a 375 px phone (card list, summary, hash equals the stored signature, 56 px targets, validation message, Keycloak step-up, signature, release, axe on every state). `AdminTests` updated for the new editor; `/approve` added to the 375 px page audit.
- Screenshots in `ManualScreenshotsTests`: `admin-workflow-steps-editor`, `admin-workflow-preview`, `mobile-approvals`, `mobile-approve-summary`, `mobile-approve-decision`.

## Decisions
- No engine features were invented (A82): no conditions, no fixed named users. A condition editor would need a `Condition` node in the parser, the executor, the map and the audit story first.
- No sticky action bar (it would cover the bottom marking banner and the content at 320 px reflow); the buttons sit at the bottom of the page.
- Phone approvals are a separate route rather than a responsive table, so desktop My tasks, its sorting and its tests are untouched.

## Not done / deferred
- Conditions, fixed assignees, delegation and escalation timers in templates (engine work).
- A per-type change diff against the previous revision in the summary (A84).
- Several drafts per workflow, draft history, and editing the same workflow from two sessions (the last save wins).
- Automatic redirect from My tasks to the phone view on a small screen (the link is one tap).
