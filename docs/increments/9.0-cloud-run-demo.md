## Assumptions
- DEMO-1: Cloud Run's writable layer is memory-backed, so `/data` counts against the 2 GiB; the seeded data is small (tens of MiB).
- DEMO-2: a single instance serves the demo; a second instance would have its own database and users could be bounced between them.
- DEMO-3: durability is not wanted: PostgreSQL runs with fsync, synchronous commit and full-page writes off.
- DEMO-4: forwarded headers are trusted from any source (the container is only reachable through the Cloud Run front end).
- DEMO-5: the REST API accepts the demo cookie instead of a demo token endpoint (ADR-0045 decision 6).
- DEMO-6: uploads are not malware scanned (acknowledged Disabled mode).
- DEMO-7: the nightly reset is not built; Cloud Run restarts or a redeploy reset the data. A scheduled redeploy or `gcloud run services update` with a changed env var resets it on demand.
- DEMO-8: Debian (noble) is used for the demo only; the UBI production base is unchanged.

## Not verified
Cloud Build and Cloud Run themselves; the image on amd64 (built and run here on arm64; every base and binary is multi-arch); behaviour under a real HTTPS front end (forwarded headers).
