## Assumptions
- GAP-B-1: Lock state is shared through the table; each node refreshes a cache every second, so another node's lock or unlock is enforced within about a second (plus the tick). A session unknown to the cache before the first load is read from the table; an unreadable table means locked. Nodes need synchronized clocks.
- GAP-B-2: Activity reports reach the table on the next tick (at most about a second late). A node that evaluates idleness in that window can lock a session whose user just acted; the error is on the safe side and the user unlocks as for any lock.
- GAP-B-3: Sticky sessions remain required for Blazor circuits and the Data Protection key ring; they are no longer needed for the lock.
- GAP-B-4: Retention is off by default; when on, the minimum is 7 days. An event is eligible when every delivery row is `delivered` and delivered before the cutoff, it occurred before the cutoff, and the notification fan-out passed it. Events without delivery rows are kept unless `IncludeUnroutedEvents`. A stalled fan-out (disabled on every node) therefore blocks retention. Pull-API backfill reaches only as far back as the retention window.
- GAP-B-5: Deletion exists only inside the audited `SECURITY DEFINER` function; the owner and superusers are stopped by triggers; the audit event, the run record and the deletion share one transaction.
- GAP-B-6: The e-mail address is typed by the user and not verified (no IdP e-mail claim is kept in the directory). `AllowedRecipientDomains` is mandatory when the channel is on. Sourcing addresses from the IdP is a follow-up.
- GAP-B-7: The mail has a constant subject and body and links to `/notifications` (not to an object): no count, kind, number, name, actor or marking. What happens to the mail after the relay is outside Keel.
- GAP-B-8: `StartTls` default; `None` needs `AcknowledgeInsecureTransport`; a relay that hides STARTTLS is refused; TLS 1.2 or 1.3; certificate and name verified, no revocation lookups (air gap); authentication PLAIN or LOGIN only.
- GAP-B-9: At most one pending mail per user and at least `MinIntervalMinutes` (10) between mails. A notification that arrives while that user's mail is being sent can be folded into it.
- GAP-B-10: A small purpose-built SMTP client instead of a dependency. No bounce or DSN processing, no OAuth or NTLM, ASCII-only content, no IDN addresses.
- GAP-B-11: Users can switch off the mail of kinds that cannot be switched off in the application (the bell still shows them).
- GAP-B-12: Broker sink deferred (ADR-0032 section 4). Revisit when a site names a broker and protocol; Kafka needs a FIPS review first.
- GAP-B-13: Spool: a full spool defers (no attempt counted, no dead letter); the receiver acknowledges by deleting a data file and its manifest; data files without a manifest are incomplete and ignored; directory fsync is not available in .NET (write-through plus rename is used).
- GAP-B-14: Finished e-mail queue rows are kept 30 days. The queue holds the recipient's user id only.

## Fix: reloading a locked session (blank page, circuit died)
Bug: with the lock state stored in the database it survives a reload or restart, so a new circuit starts for an already-locked session. Page components ran and called `CurrentUser.GetAsync` before `MainLayout` had decided the session was locked; `SessionLockedException` was unhandled and the circuit died (blank page, `ObjectDisposedException` in the log).
Fix: `MainLayout` renders `@Body` only once `ready` (lock state and user known, as with the supplier flag) and not locked, so on first load and reload of a locked session only the lock dialog is rendered and no page component runs or fetches data. `@Body` is wrapped in `Components/Layout/SessionLockGuard.razor` (an `ErrorBoundaryBase`): a `SessionLockedException` (a lock landing mid-render) is swallowed, renders nothing and the layout's lock panel shows; every other exception is thrown again from the guard's render and reaches the renderer as unhandled, as before. The guard recovers on its next parameter update, so a lifted lock renders the page again.
Tests: unit `SessionLockTests` (already-locked circuit never runs the page, mid-render lock, guard swallows only the lock exception, other exceptions pass); E2E `SessionLockTests.Reloading_a_locked_session_shows_the_lock_dialog_without_page_data_or_a_circuit_error` (lock, reload, dialog and countdown visible, no page data in the DOM, no console, page or server-log circuit error, unlock through Keycloak). The existing no-DOM-leak E2E tests are unchanged.
