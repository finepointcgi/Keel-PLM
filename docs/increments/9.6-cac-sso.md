# 9.6 Production sign-in: CAC/PIV, customer IdP SSO and the Sign-in status page (2026-10-30)

ADR-0058. No migration. Assumptions A88 to A90 (SIGNIN-n below). Operator guides: [ops/cac-piv-sign-in.md](../ops/cac-piv-sign-in.md), [ops/sso-integration.md](../ops/sso-integration.md).

## Delivered
- **CAC/PIV (X.509) through Keycloak, opt-in.** `deploy/compose/keycloak/overlays/cac-piv/`: `configure-cac-piv.sh` (kcadm only; idempotent; creates the browser flow `keel-cac-browser`:
  cookie, a level-1 conditional flow with the X.509 authenticator (plus the password form when `CAC_FALLBACK=password`), a level-2 conditional flow with the certificate only),
  `x509-config.json` (EDIPI regex on the subject DN to the user attribute `edipi`, timestamp validation, key usage, CRL from a local file failing closed, OCSP and CRL
  distribution point as switches), `map-credential.sh` (maps one EDIPI to one Keycloak user, refuses a malformed or already assigned value). Optional dev overlay
  `deploy/compose/compose.cac-piv.yaml` (checked with `docker compose config` only).
- **Test PKI.** `scripts/idp/generate-test-pki.sh`: throwaway CA, server certificate, valid CAC-shaped client certificates for two users (CN `LAST.FIRST.T.EDIPI`, UPN and e-mail SAN),
  and an unknown-EDIPI, an expired, a revoked (with CRL) and an untrusted-CA certificate. Every subject says "KEEL DEV TEST PKI NOT FOR PRODUCTION".
- **Certificate level for e-signatures.** `Keel:Auth:StepUpAcr`: the step-up sends `acr_values`, the ID token must carry that `acr` (else refused and audited as
  `session.step_up` denied, `step_up.acr_not_satisfied`), and `StepUp.IsFresh` (workflow signatures, task detail) and the requirement verification check the signer's `acr`
  too. `Subject.Acr` (new, optional), `WorkflowOptions.StepUpRequiredAcr`, `RequirementOptions.StepUpRequiredAcr`, `StepUp.Verdict.AcrNotSatisfied`, the RFC 9470 `acr_values` in the
  API's 401 step-up challenge. The OIDC handler drops `acr` by default; `KeelUi` keeps it from the ID token like `auth_time`.
- **Customer IdP brokering templates.** `overlays/idp-broker/oidc-broker.overlay.json` and `saml-broker.overlay.json` (identity provider and five role plus six attribute
  mappers, signature validation on, `trustEmail` off, FORCE sync, no default role) and `scripts/idp/merge-realm-overlay.sh` (jq merge, named placeholders, secrets from files,
  refuses leftover placeholders and duplicate aliases).
- **Sign-in status page** `/admin/signin` (`Administration > Sign-in`; AdminNav link and Administration home entry), read-only (`SignInPage`, `SignInAssessor`, `IdpProbe`, `SignInSettings`): effective settings with
  the setting that controls each, warnings worst first, the administrator's own `acr`/`amr`/`auth_time` and which security claims arrived (names only), and a button that reads the
  IdP discovery document at the configured authority. Settings `Keel:Auth:SignIn:Method` (Password, Certificate, Federated; anything else stops the start),
  `Keel:Auth:SignIn:PasswordFallback`, `Keel:Auth:StepUpAcr`; Helm values `config.auth.signInMethod|passwordFallback|stepUpAcr` (rendered only when set, because `verify-helm.sh` refuses credential-looking text) and `KEEL_STEPUP_ACR` in the compose prod example.

## Tests
- Unit `SignInStatusTests` (14): every warning rule (password in production versus development, fallback, a password that could sign, demo, http authority and metadata, hardening gaps, worst
  first), discovery parsing and comparison, the administrator's own session observation, the `acr` rule at signing (`IsFresh` with a required level: exact, absent, stale), the step-up
  verdicts, `acr` reaching the `Subject`, method normalization, and the page (read-only: no form, no input, one button; discovery check shows a failure as a message).
  Whole unit suite: 1493 tests; `ClamdScannerTests.Large_stream_is_scanned_with_bounded_memory` fails under load from other test runs on the machine and passes alone (not related).
- Integration `Keel.IntegrationTests.Idp` (20, real Keycloak 26.4 containers, generated test PKI, ephemeral ports, run under /tmp/keel-int.lock):
  `CacPivSignInTests` (9): valid certificate signs in as alice with her roles and attributes; another certificate as bob; trusted certificate with an unmapped EDIPI refused (`user_not_found`
  in Keycloak's log); expired refused; revoked refused (log: "Certificate has been revoked", same EDIPI and valid dates as alice's); untrusted CA refused; no certificate and no password
  form; step-up with `acr_values=2` returns `acr` 2, the same subject and a newer `auth_time`; the overlay script is repeatable and `map-credential.sh` refuses a malformed, unknown-user
  or already assigned identifier. `CacPivPasswordFallbackTests` (4): password logs in at level 1 only; a correct password cannot satisfy level 2; a certificate still reaches level 2;
  an unmapped certificate lands on the password form (the weakness of that policy, asserted). `OidcBrokerTests` (4, two Keycloaks): just-in-time user with mapped roles and attributes
  (and no `plm-admin`/`plm-viewer`), an unmapped upstream user gets no `plm` role and no security claims, an upstream user with a local user's e-mail is not linked ("already exists" step),
  the SAML template imports and the realm publishes service provider metadata. `MergeOverlayScriptTests` (3): a filled template merges with quotes and backslashes intact, a missing value
  names the placeholder and writes nothing, an existing alias is refused.
- Packaging: `scripts/verify-helm.sh` passes with the new values (they render only when set).
- NOT run: the full integration suite and the Playwright E2E suite (the shared-seam edits are additive and covered by a targeted regression run of 51 existing integration tests on signing, step-up, requirement verification, baselines and MBOM release, which passed), and nothing against real cards or a customer IdP.

## Assumptions
- SIGNIN-1 (A88): the identifier is the EDIPI (regex, attribute `edipi`), nothing else of the certificate becomes an attribute; local CRL file fails closed.
- SIGNIN-2 (A89): `Keel:Auth:StepUpAcr` (empty by default) binds signatures to an `acr`; PIN re-prompt at step-up is middleware behavior, not asserted.
- SIGNIN-3 (A90): just-in-time users get only what the IdP asserts; no auto-link, no inferred U.S.-person status, no Keel-side provisioning rules, no automatic de-provisioning.
