## Assumptions (FEAT-REQ-n)
- FEAT-REQ-1: A specification is revisioned like an MBOM (A, B, ...; iterations; locked while Under Review, Released or Obsolete). Release is by review with signatures; submitting needs at least one requirement and none left in Draft (approve, defer or withdraw
  first). There is no check-out: an edit batch is one new iteration of the latest In Work revision. Releasing a revision makes the previous Released one Obsolete.
- FEAT-REQ-2: Requirements are permanent identities (`R-0001`, unique per specification) and are never deleted; withdrawal is a status. Deferred and withdrawn requirements are not counted as gaps. At most 5,000 requirements, 10 levels.
- FEAT-REQ-3: A requirement's markings are at least as restrictive as its specification's; the form offers a confirmed raise. Changing the specification's markings needs a reason, is allowed only In Work, and can raise requirements.
- FEAT-REQ-4: Restricted requirements are placeholders (outline number and depth) in the outline; they are not drawn in the graph and are absent from matrix, coverage and exports. A link to a restricted end, and a link from a restricted requirement seen from a part,
  document or change, is a placeholder with no type, key or title; the placeholder rows are shown, counted nowhere. Placeholders reveal that something restricted is linked (the standard where-used and impact redaction), never what.
- FEAT-REQ-5: Coverage is the reader's coverage. Allocated = an allocation-role link whose part the reader can read (within a baseline: the part is in it); Verified = Verified or Waived for the current content; planned verification = a verification-role link to a readable document.
  A requirement whose only allocation is hidden from a reader is unallocated for that reader. Coverage of an earlier revision uses the links as they are now and the verification valid for that revision's content.
- FEAT-REQ-6: Suspect: a link is suspect when the source requirement or a requirement target changed after the link was reviewed (marked in the edit's transaction, one audit event per link), or when a part or document target has a newer revision than the reviewed one
  (computed on every read; persisted with audit by the sweep, every `Keel:Requirements:SweepSeconds` (default 300, 0 = off) and on demand by an administrator). Links to changes never go suspect by revision. Review needs modify access and a readable other end.
- FEAT-REQ-7: Verification records are immutable; the newest record for the exact current content decides (Verified, Waived, Failed); older content is Stale. A waiver needs a reason. A formal record needs the approver role, a sign-in no older than
  `Keel:Requirements:StepUpMaxAgeSeconds` (default 300), a meaning and, for a pass, at least one evidence document; the evidence must be readable by the signer. A formal record has its own signature row (SHA-256 over the record, requirement hash, evidence, signer and time).
- FEAT-REQ-8: Notes and waiver reasons are stored with the requirement's markings and appear only to readers of the requirement; audit events and notifications carry keys, numbers, codes, hashes and counts only (an architecture test checks the audit statements).
- FEAT-REQ-9: Import: formats csv, excel (any of comma, semicolon or tab; byte-order mark; spreadsheet header names) and reqif (ReqIF-style: spec objects with string attributes and a specification hierarchy; DTDs refused). Files up to 2 MB and 5,000 rows. Blank cells keep the existing value (update) or
  take a default (new: functional, medium, test, draft). An id that is not a readable requirement of the specification makes a new requirement (so a hidden requirement is indistinguishable from a missing one). Nothing is deleted by an import. Apply requires the digest of the preview.
  Export writes only readable requirements, a banner line, and guards spreadsheet formulas with a leading apostrophe.
- FEAT-REQ-10: Link types are administrator data (retired, never deleted; the five system types cannot be retired or redefined; an allocation role needs a part target, a verification role a document target). A link between requirements cannot make a requirement depend on itself.
- FEAT-REQ-11: `reqspec` is an awareness kind (follow, comment, recent, favorite). The object-type constraints of `ws` and `ntf` are found by definition and replaced by a pattern (migration 0020 already did; 0021 repeats it idempotently). Saved-search scopes do not include requirements (the search page and palette do).
- FEAT-REQ-12: The Trace tab and the impact analysis show requirements by specification and key with title and link relation. The page banner covers the requirements shown.
- FEAT-REQ-13: The requirements API is its own OpenAPI document; the cookie export route is excluded from it.
- FEAT-REQ-14: The Draft gate and the digest binding use the system view of all rows, including requirements the submitter cannot read; the refusal message does not say which.

## Not built / not verified
- ReqIF is a documented subset (no datatypes, spec types or relations); tool-specific ReqIF files may need mapping. Requirement-to-requirement links across specifications are supported, but a requirement cannot move between specifications.
- No requirement-level workflow, no change-driven requirement revisions (a specification is revised as a whole; an ECN can be linked with the changed-by type), no coverage history or trend, no Quality-module records yet (they can arrive as link types).
- Suspect links notify the specification's watchers (pointer only), not the individual requirement owners.
- See the hand-off report for the test run results; the browser end-to-end tests and the axe audit are listed there with what ran.
