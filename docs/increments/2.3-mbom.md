# Increment 2.3: EBOM / MBOM and reconciliation (2026-10-28)

Design and rules: [ADR-0024](../adr/0024-ebom-mbom.md). Migration `0011_mbom.sql`.

## Delivered
- **MBOM as its own versioned object** per (part, plant): header `MB-nnnnnn`, revisions, iterations, check-out working copy, lines, EBOM equivalence links, derivation record, lifecycle `mbom-default`, release through the review workflow (`mbom-release-review`).
- **Generate from EBOM** (Latest, LatestReleased, effectivity unit, baseline, explicit version), multi-level per plant, and **regeneration as a proposal** accepted line by line or in bulk into a new iteration that keeps manufacturing edits.
- **Reconciliation**: pure engine, persisted immutable runs with digests, severities, overall status (Reconciled / with exceptions / Not reconciled / Stale), release gate bound into the signed hash, per-plant warning policy.
- **Queries**: explosion per plant (filter and redaction inside the recursion, lazy expansion, as-of unit), purchasing summary with scrap, CSV, compare, where-used by plant, EBOM|MBOM side by side.
- **REST** `/api/v1/mboms/...` (search, create, generate, get, lines, working copy edits and links, derivation, check-out/in/undo, transition, revise, markings, regenerate propose/apply, reconcile, runs, explosion, csv, summary, compare, side-by-side, where-used, plants, supply types, review) and the cookie route `/ui/mboms/{n}/explosion.csv`.
- **UI** (`Pages/Mbom/`): list with plant selector and plant administration, MBOM page (header, virtualized lines grid with EBOM-link indicators, working-copy editor with links and EBOM source, release review panel, reconciliation panel with grouped findings and history, update-from-EBOM proposal, multi-level structure), generate wizard, side-by-side, compare, and a "Manufacturing BOMs" section on the part page.
- **Integration points**: `IManufacturingBomSource` (released MBOM with resolved children, for the Phase 4 ERP publisher) and `IManufacturingImpactProvider` (ECN impact lists stale MBOMs per plant).

## Performance (warm, this machine)
Reconcile 5,000 vs 5,000 lines: about 0.23 s end to end (budget 1 s). 50,000-line, 10-level MBOM explosion: about 0.65 s (budget 2 s). Generate 5,000 lines: about 1.1 s. Existing EBOM gates pass unchanged.

## Assumptions (MBOM-n)
- **MBOM-1** An MBOM is one object per (part master, plant), revised independently of the design revision; releasing a revision supersedes the previous Released one. Lifecycle `mbom-default` is view-only in the admin UI.
- **MBOM-2** MBOM markings dominate the part's, not the lines'; reading needs Read on both; lines of unreadable parts are placeholders.
- **MBOM-3** Plants and supply types are tables of their own (plant release policy); Make, Buy, Consume are system codes. `Consumable` is a seeded part type.
- **MBOM-4** `quantity` is net; `scrap_factor` is a fraction; requirement = quantity x (1 + scrap), compounded through levels in the explosion. Reconciliation compares net quantities (tolerance 0.00001), never converts units.
- **MBOM-5** Manufacturing-only is a line flag (`mbom_only`), not a link status; an MBOM-only line has no links.
- **MBOM-6** Links are carried to a changed EBOM by identity (part, find number, alternate), else (part, find), else the only line of the part.
- **MBOM-7** Reconciliation compares complete data; reading filters. A finding about an unreadable part keeps code, severity, find numbers and quantities.
- **MBOM-8** Stale means revision drift is the only error. Reconciled with exceptions means warnings or declared notes exist. Errors always block release; warnings block only where the plant says so (default: allowed).
- **MBOM-9** An MBOM has at most 5,000 lines; a multi-level generate creates at most 200 MBOMs; explosion caps equal the EBOM's.
- **MBOM-10** A Make sub-assembly is a child of type Assembly, source Make, on a line with supply type Make; it needs an MBOM in the same plant (missing is an error, unreleased a warning). Buy items are leaves.
- **MBOM-11** Generation and regeneration are refused when the EBOM contains parts the caller cannot read (like baselines).
- **MBOM-12** MBOM cycles are not prevented at edit time (MBOM lines can name any part); the explosion flags and stops at a circular reference.
- **MBOM-13** Freshness for release: Latest, LatestReleased and effectivity specs are re-resolved; baseline and explicit-version runs are immutable and always fresh.
- **MBOM-14** The ECN impact list shows the latest non-obsolete MBOM revision per plant that was derived from the part, flagged when the EBOM has already moved on.
- **MBOM-15** The operation reference is a free-text key (A18); no routing is modelled.

## Not done / deferred
- Making `mbom-default` editable through the admin lifecycle editor (needs `mbom` in `LifecycleRules.VersionedObjectTypes` and protected states in Keel.Admin).
- UI for changing an MBOM's markings and for administering supply types (both exist in the API and service); no UI for choosing the revision of a Make child other than "latest released / latest".
- Obsoleting MBOMs when their part is obsoleted, and revising an MBOM inside an ECN, are not modelled; the impact list is the warning.
- ERP publishing and TDP export are the integration module's (Phase 4); `IManufacturingBomSource` is the read API for it.
- E2E covers generate, reconcile, structure, side by side and the part page, not the working-copy editing flow (covered by integration and bUnit tests).
