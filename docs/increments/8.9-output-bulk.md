# 8.9 Output and bulk work (2026-10-29)

ADR-0044. Migration `0027_reports.sql` (schema `rpt`). OpenAPI: `docs/reports/openapi.json` (`/openapi/reports.json`). New module `Keel.Reports`; ports in `Keel.Core/Reports/ReportPorts.cs`.

## Delivered
- **Release package PDFs**: for a released part or assembly, ECN or established baseline: cover sheet, BOM report, document list with file SHA-256, signature page (signer, meaning, decision, UTC
  time, comment), change summary. Aggregate banner plus every distribution notice at top and bottom of every page. Refused (never redacted) when any included object is unreadable. Stored
  content addressed in the vault, immutable `rpt.artifact` row, audited, downloadable only while the caller may read every included object.
- **Excel and CSV BOM exchange**: export of the resolved EBOM (latest, released or as designed for one unit) or MBOM, with variant selection through `IVariantSelectionSource`, effectivity, find
  numbers, option condition and a markings column; banner rows on top; formula neutralization. Import template, reviewable proposal with row-level dry run, apply through `ICadPartPort`
  (BOM working copy, check-in, release locks, audit), repeatable apply; ZIP-bomb, entity-expansion and size limits.
- **Mass change** of parts: set an attribute, change markings (within the user's authority), add to a baseline proposal, submit for review, watch, favorite. Preview with per-object verdict and
  reason; per-object apply through the normal services under one correlation id; partial failure report; repeatable; undo for reversible operations; hard caps.
- **Report builder**: eight datasets (parts, bill of materials, changes, baselines, quality records, requirement sets, compliance declarations, retention schedules), selectable columns, filters,
  sort, grouping with counts, saved and shareable definitions, aggregate banner, export to CSV, .xlsx and PDF.
- **UI**: `/output/reports`, `/output/packages`, `/output/bom`, `/output/mass` (navigation group "Output"); **REST** `/api/v1/output/...` with its own OpenAPI document; UI download routes under `/ui/output/...`.
- Shared edits (all additive): `Keel.slnx`, `Keel.Api.csproj`, `Keel.Web.csproj`, `Program.cs` (two lines), `NavModel` (one group), `ActivityCatalog.HiddenPrefixes` (`output.`),
  `VaultReferences.Sources` (`rpt.artifact.sha256`), `scripts/update-openapi.sh`, architecture test module table, navigation test expectations.

## Assumptions
- **FEAT-OUT-1** PDFsharp 6.2.4 (MIT, already in the tree) with the embedded DejaVu Sans faces; QuestPDF (conditional community license, native binaries) and a hand-written writer were rejected (ADR-0044).
- **FEAT-OUT-2** A package is made only for released data: a part or assembly whose latest revision is Released, an ECN that is locked (released or closed), a baseline that is Established. Structure
  is resolved at "latest released" for children; a line with no released revision refuses the package.
- **FEAT-OUT-3** A package includes the documents linked to the root and, for a part, to its first 100 distinct child parts; documents carry the file names, sizes and SHA-256 of their latest iteration.
  Signatures are those of the release review of the root revision. The change summary is the change the revision is bound to (parts) or the ECN itself.
- **FEAT-OUT-4** The artifact row has no marking columns; access is "can read every listed object now". A package therefore disappears from lists when markings change, and returns when they allow it again.
- **FEAT-OUT-5** A package of more than 5,000 BOM lines is refused; at most two packages render at once (a busy answer, 503).
- **FEAT-OUT-6** The package PDF cannot contain its own SHA-256; the hash is in the record, the audit event and the download headers.
- **FEAT-OUT-7** .xlsx is written and read by an in-house implementation (inline strings, first sheet only); .xls, .xlsm, workbooks with external links or embedded objects are refused. CSV import is UTF-8.
- **FEAT-OUT-8** Neutralization prefixes an apostrophe to text beginning with = + - @ tab or CR, in both formats; import removes that apostrophe again so a re-imported export is unchanged. A genuine note starting with
  an apostrophe and a formula character loses the apostrophe.
- **FEAT-OUT-9** Import supports the actions add, update, remove on direct children of one or more unlocked assemblies per file (at most 5,000 rows); it changes the latest iteration through check-out and check-in
  (new iteration), refuses released parents (use an ECN), and checks designator counts against quantity for unit EA in the dry run. Import never creates parts.
- **FEAT-OUT-10** A proposal and a mass change belong to their creator (nobody else can read them, not even administrators); part numbers in them are re-authorized when a mass change is shown.
- **FEAT-OUT-11** Export of an unreleased or moving structure is allowed ("latest" spec); the file says which spec it used. Export is capped at 100,000 lines.
- **FEAT-OUT-12** "Baseline proposal" is a saved named list of parts per user (`rpt.baseline_proposal`); creating the baseline itself stays in the baseline service over a root structure.
- **FEAT-OUT-13** Mass change classification is not offered (class values belong to an iteration and are validated against the class's attributes): attribute change covers the part attributes. Markings changes on
  locked revisions are refused (they go through change control). Submit for review takes reviewer login names per slot; it is not reversible. No operation in this increment requires an e-signature; the apply loop
  stops at a step-up requirement and reports the rest as waiting.
- **FEAT-OUT-14** Watching and favoriting add to what the user already has; undo restores the previous watch level or removes the favorite only if the mass change added it.
- **FEAT-OUT-15** Report rows are capped at 5,000 per run (the first 5,000 in the owning service's default order; the result says "limited"); column filters, sort and grouping are in memory over those rows.
  Text search is pushed to the owning service. A saved definition can be shared with everyone (read-only); definitions hold no row data. At most 100 definitions per user.
- **FEAT-OUT-16** The "schedule" dataset is the records retention schedules (records managers, administrators and auditors only, as the owning service decides). A programs schedule module is being built
  in parallel and is not on main; its dataset joins later by registering another `IReportDataset`. The "requirements coverage" and "compliance roll-up" datasets list requirement sets and declarations; the per-product coverage
  and roll-up computations stay on their own pages because they need a structure and are not list queries.
- **FEAT-OUT-17** Scheduling of reports is out of scope (no scheduler, no mail). No new notification kind: output is requested and delivered in the same interaction, so `INotificationSink` has no fitting event.
- **FEAT-OUT-18** The activity feed hides `output.*` events (a person's own exports are not colleagues' news).
- **FEAT-OUT-19** Limits: 500 objects per mass change, 20 mass changes per user per hour, 12 filters per report, 30 columns, 5 MB import file.

## Tests
Unit (23 in `ReportsUnitTests`): workbook round trip, formula triggers in xlsx and CSV, decompression bomb by size, lying sizes cut while reading, part-count/macro/external-link/path refusals, DTD refusal, row/column/cell
limits and formulas not evaluated, import template parsing with per-row errors, banner and notices on every page of a multi-page package (PdfPig), report filter/sort/group/banner, refusal of unknown columns, operators and sort keys,
exports with banner in three formats, structure rules (no non-`rpt` SQL, `output.` actions, immutable artifact, vault registration, endpoints require a role).
Integration (10 in `ReportsTests`, real host, PostgreSQL and vault): package stored, immutable, hash equals vault object, every page marked, listing and download denied for a reader of fewer objects (audited), refusal with a
count and nothing stored; BOM export read filtering and injection safety; import dry run, apply once, audit and new iteration; mass change preview reasons, partial failure, retry, shared correlation id, undo, ownership; markings authority, watch,
favorite, baseline proposal; caps and rate limit; **SQL/policy oracle for every dataset over seven subjects and six marking variants** (exact for parts, BOM placeholders and changes; every dataset checked not to fail and rows marked as shown);
saved and shared reports, exports with banner, REST; OpenAPI document equals the committed one.

## Results of the runs (2026-10-29)
Unit 1190 passed (23 new); integration 770 (10 new; the one failure of the full run, the vault schema guard flagging a column named `shared`, was fixed by renaming it `visible_to_all` and re-run green with the vault tests);
E2E: the 4 new `OutputTests` pass, and the axe audit passes in light, dark and high contrast at 1280 px and in light at 375 px with the four new pages in the list (the 375 px high-contrast variant and the rest of the E2E suite were not re-run).
The browser test found a real defect: the marking header of the download routes carried a non-ASCII banner (now percent-encoded like the other downloads).
