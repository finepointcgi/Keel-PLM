# ADR-0060: Production packaging, preflight, and the operations proof (backup and restore, upgrade rehearsal, load smoke)

Status: Accepted

## Context
The compose production example, the Helm chart and the offline bundle exist (ADR-0012, ADR-0020) but had gaps a production operator would hit: no resource limits in compose, no health check on the vault and the proxy, no preflight, no machine-readable versions manifest, a backup and restore test that covered the database only (physical backup and WAL, no vault, no logical dump), no vault integrity verifier (a documented Phase 5 gap), no rehearsal of an upgrade against data, and no measured end-to-end latency.

## Decision
- **Production bundle = the compose file and chart that already exist, hardened.** `compose.prod-example.yaml` (the name is kept so installed sites and scripts keep working; the documents now call it the production compose bundle) gets memory, CPU and pids limits for every service (defaults overridable per site in `.env`, see `docs/ops/performance.md` for what the load smoke measured), healthchecks on the vault and the proxy, and the application waits for a healthy vault. `scripts/verify-packaging.sh` renders the file and asserts these properties for every service (healthcheck, limits, non-root, read-only root except the one documented vault exception, dropped capabilities, no-new-privileges, digests, secrets from files, one published port). The Helm chart is verified by `scripts/verify-helm.sh` (lint, render, schema, security properties).
- **One command, with preflight.** `install.sh` and `upgrade.sh` run `preflight.sh` after verifying the signed bundle and before loading any image or writing anything: runtime and compose version, daemon access, memory, disk, port, FIPS state against `KEEL_REQUIRE_FIPS`, certificates (parse, expiry, key match, chain to `ca.crt`, names for the public host, `postgres` and `vault`), secret file, IdP reachability (a warning: the containers' route may differ), and for upgrades the installed version, the health of the running application and the number of applied migrations; Kubernetes mode checks helm, kubectl, the cluster and that the values file renders against the chart schema. `install.sh --preflight-only` stops after the checks. Failures stop before anything is loaded or changed; warnings are printed.
- **Versions manifest.** The offline bundle carries `versions.json` (bundle version, git revision, build time, every image with reference, archive file, SHA-256 and size, the chart file, the tool versions, and every migration file with its SHA-256, which equals what `public.schema_migrations` stores) and it is covered by the signed `SHA256SUMS`.
- **`keel-vault verify`** (new, read-only): reads every object that the reference registry (`VaultReferences.Sources`, with each source's live predicate and size column) says the database needs and checks existence, recorded size and SHA-256 of every byte. It closes the "bulk vault verifier" gap of `docs/ops/backup-restore.md` and is the vault half of every restore check.
- **Operations proof by scripts that run for real**, each starting only throwaway containers and volumes named `keel-drill-*` that it removes itself, never touching existing containers, volumes, networks or the dev and demo ports:
  - `scripts/ops/backup-restore-drill.sh`: real migrator and services populate parts and documents with files; `pg_dump -Fc` plus `pg_dumpall --globals-only`, a cold copy of the vault volume taken after the dump, SHA-256 manifest; the source is destroyed; a fresh PostgreSQL and a fresh vault volume are restored; all-table row counts, `keel-audit verify` (chain and signed checkpoints), `keel-vault verify` and a byte-for-byte read of every document file are compared with the source; negative controls (a tampered audit row, a damaged and a deleted vault object) must be caught. It complements `scripts/backup-restore-test.sh` (physical backup, WAL and point in time recovery, database only).
  - `scripts/ops/upgrade-rehearsal.sh`: a database at the previous migration set (every migration file of the previous release, taken from git history by tag or commit, default the last commit before the newest migration files) is populated through the services of that release's schema where compatible, then the current migrator applies the newer forward-only migrations; rows, audit chain and migration hashes are verified before and after.
  - `scripts/ops/load-smoke.sh` with the in-repo client `tests/Keel.LoadTool` (no third-party tool; k6 is AGPL): the production image with its shipped limits against a throwaway stack with real Keycloak tokens, p50/p95/p99 and error counts for list, search, create-part and BOM expand at several concurrencies.
- **Results are recorded as measured**, in `docs/ops/drill-results/` with the commands, and `docs/ops/backup-restore.md`, `upgrade.md`, `performance.md` and manual chapter 24 quote them with their limits. Nothing is estimated.

## Consequences
- A restore is no longer "believed to work": the evidence and the way to repeat it are in the repository, and CI runs the drills nightly.
- The vault copy in the drill is a cold volume copy (the vault stopped for the copy). Sites with replication or snapshots use their own mechanism; `keel-vault verify` is the check that applies to all of them.
- The load smoke measures one machine with the load client on the same host; it states the limits of what it shows and is not a capacity guarantee.
- `helm` was used for lint and render only; no Kubernetes cluster was available, so the chart and `install.sh --k8s` were not installed into a cluster in this increment.
