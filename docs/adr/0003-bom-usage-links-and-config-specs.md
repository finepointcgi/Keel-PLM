# ADR-0003: BOM usage links and configuration specifications

**Status:** Accepted · 2026-10-27

## Context
A released assembly must stay stable while children keep evolving, and different users need different views (latest work, latest released, as-of-effectivity, baseline). Target: 10 levels / 50k lines in < 2 s (A11).

## Decision
- A **usage link** goes from a parent **iteration** to a child **master** with: quantity, unit of measure, find number, reference designators (stored as an array, validated against quantity for EA lines), line notes, and (Phase 2) effectivity.
- The child version is resolved at read time by a **configuration specification**: `Latest`, `LatestReleased`, `Effectivity(serial|lot|date)` (Phase 2), `Baseline(id)` (Phase 2).
- Explosion is one recursive CTE in PostgreSQL that resolves the config spec per level and joins the **access filter** generated by ADR-0004, returning a flat ordered list (path, level, line). The UI requests levels lazily; full explosion is available for export and reports.
- Lines the user may not see are returned as **redacted placeholders** (A4) and are not expanded further.
- Where-used walks links in reverse (child master → parent iterations → their revisions), filtered by config spec.
- EBOM and MBOM (Phase 2) are distinct structure types sharing the link model, joined by an equivalence link for reconciliation.

## Consequences
- Cycle detection runs on link creation (a recursive check), not during explosion.
- Indexes: `(parent_iteration_id)`, `(child_master_id)`, plus `is_latest`/`state` on revisions. A performance test with 50k synthetic lines is a CI gate from increment 1.4.

## Alternatives
- Links to child *revisions* (fixed): simple but forces parent revisions for every child change; rejected.
- Materialized exploded BOM tables: fast reads, painful invalidation; may be added as a cache later if measurements require.
