# ADR-0022: Administrator configuration through the UI, versioned lifecycles, and hierarchical classification

**Status:** Accepted · 2026-10-28 · Implements increment 2.2; builds on [ADR-0002](0002-versioned-object-model.md), [ADR-0004](0004-abac-and-markings.md), [ADR-0006](0006-workflow-engine.md), [ADR-0013](0013-testing-strategy.md), [ADR-0014](0014-blazor-server-ui.md), [ADR-0018](0018-workflow-and-esignature.md) and [ADR-0019](0019-change-management.md)

## Context
The product requirement is that types, attributes, lifecycles and workflows are configured through the UI, not code, and that parts are classified with admin-defined attribute sets. Phase 1 already stored most of this as data (attribute definitions, lifecycles, workflow templates, reason codes) but only a seed migration and a template upload API could change it, and several lists were compile-time constants (part types, sources, units, document types, priorities, number prefixes).
Configuration is dangerous to change live: an attribute edit can invalidate stored values, a lifecycle edit can strand released objects, and a classification move can orphan values. Every change therefore has to be validated, audited with before and after values, and previewed.

## Decision

### One module, one transaction pattern
- New module `Keel.Admin` (references only Core, Security, Audit). Every command goes through `AdminRunner`: administrators only (a denial is audited as `admin.*` with outcome Denied), one transaction for the change and its audit event (`before`/`after` canonical JSON, `reason`), database constraint violations surfaced as messages, and no audit event for rejected input. Reads are administrator-only too (configuration is not marked data, so they are not audited).
- Workflow templates are managed through `IWorkflowTemplateAdmin` (Keel.Core), implemented by `Keel.Workflow.WorkflowTemplateAdmin`. It reuses the engine's parser and the audited 1.5 upload (`workflow.template_upload`), and owns the new `wf.template_pin`. Keel.Admin never references Keel.Workflow.
- Configuration history (`ConfigHistoryService`) reads the tamper-evident audit log (objects `configuration` and `workflow_template`) and computes the differences from the recorded before/after values. Administrators may read it because the events hold configuration only; the full log stays with the auditor role.

### Data model (migration 0009)
- **Attribute definitions** gain help text, group, format (regex over the whole value, 250 ms timeout), range, `retired` and a revision counter. Retiring is soft: stored values stay readable on every iteration and are carried forward unchanged; a retired attribute is never required or re-validated. The data type of an attribute that has stored values never changes (guidance: create a new attribute, copy values by check-in or import, retire the old one); enum values in use cannot be removed.
- The validation logic moved to `Keel.Core.AttributeSpecs` so part attributes and class attributes are validated by one implementation; `Keel.Parts.AttributeValidator` delegates to it with unchanged messages.
- **Lifecycles are versioned.** `plm.lifecycle_family` (current version) and version columns on `plm.lifecycle`. Version 1 keeps the family name as its id (`part-default`), version n is `<family>~v<n>`, so every existing row, foreign key and trigger keeps working. Database triggers make a published version immutable (states, transitions, header); a version is inserted as a draft and published after its rows exist; the family's current version only moves forward. New objects take the family's current version; an object keeps its version until the audited `cfg.migrate_lifecycle_objects` operation, which needs a state mapping covering every state in use, never maps a locked state to an unlocked one, refuses states with checked-out revisions when the target is locked, and refuses objects under an active review.
- Validation rules (`LifecycleRules`, pure): exactly one initial and unlocked initial state, reachability, no dangling/self/duplicate transitions, a locked state for release-style lifecycles, `workflow` transitions only where a template is active for the object type (workflow transitions an existing version already has are kept), and the states and transitions the engines refer to by name (In Work, Under Review, Released, Obsolete; the part review and change transitions) cannot be removed or retagged.
- Part and document types may bind a lifecycle family (`cfg.ref_item.lifecycle_family`): this is what makes "create a lifecycle" useful.
- **Reference lists** (`cfg.ref_item`): part types, sources, units, document types, change priorities, change class labels, and the office and program pickers. Items are retired, never deleted. Services validate inside their own transaction through `Keel.Core.ReferenceChecks`; the old CHECK lists are dropped and a trigger refuses a retired item for new rows. UI pickers read a cached `IReferenceData` (30 s, invalidated by an admin write in the same process).
- **Numbering** (`cfg.numbering`): prefix and width per object type; the counter stays a PostgreSQL sequence that only moves forward (advance sets it up, never down); a prefix change that would collide with an existing explicit number is refused. Change prefixes are fixed because the `chg` tables check the number format.
- **Template pins** (`wf.template_pin`): `WorkflowService.StartAsync` uses the pinned template when the caller names none; an explicit choice wins.
- **Reason codes and signature meanings** stay in their tables (`wf.reason_code`, `chg.reason_code`); administrators add, edit and retire them. The decision of an existing meaning cannot change (signatures carry it) and every review and approval keeps an approving and a rejecting meaning.

### Classification
- `cfg.class_node` (materialized path of codes, depth <= 12, active/retired, never deleted, code immutable) and `cfg.class_attribute` (same shape as part attributes). The effective attribute set of a class is its ancestors' attributes (root first) followed by its own; names are unique along every root-to-leaf path.
- **Move** checks cycles, depth, name clashes with the new ancestors and then validates every classified latest iteration and working copy in the subtree against the new effective sets; any conflict refuses the move with an exact count and, for parts the administrator may read, examples. **Retire** is refused while subclasses are active or parts are classified in the class. Attribute edits run the same impact check, so a tightened rule cannot strand classified parts.
- **The class of a part is iteration-owned data** (ADR-0002): `cfg.part_classification` per iteration (immutable, with typed value rows `cfg.part_class_value` for search) and `cfg.part_checkout_classification` for the working copy (deleted with the check-out). `ClassificationParticipant` (an `IPartIterationParticipant`) copies the latest iteration's classification into the working copy at check-out, validates and freezes it at check-in (vetoing a retired class or invalid values), copies it forward on revise, and describes it in `DescribeContentAsync`. A new default member `CoveredByReviewSignature` lets the part review gateway fold that text into the signed content (`$owned` key in the signed attributes) for classified parts only, so existing signature hashes (and the BOM, which does not opt in) are unchanged; the ECN fingerprint already includes every participant.
- **Search** (`ClassificationService.SearchAsync`): class subtree, free text, state and typed attribute filters over the frozen values of the latest iteration. Every statement (page, total, class-tree counts, per-attribute facets) is built in one place with `AccessPolicy.BuildReadFilter` interpolated, and facets ignore their own filter (standard facet semantics). A test proves totals, class counts, enum value counts and numeric ranges equal an in-memory oracle over `AccessPolicy.Evaluate` for five kinds of user.
- **Why typed rows rather than a GIN index:** equality and ranges per attribute are served by partial b-tree indexes on `(attr, num)`, `(attr, txt)`, `(attr, flag)`; a GIN `jsonb_path_ops` index handles containment but not numeric ranges. Measured on 5,000 classified parts (diameter range 20 to 22 and grade 316, under the access filter): the service answered in 20 ms after warm-up and the same-shaped statement executed in 0.8 ms with a bitmap index scan on `part_class_value_num_idx` (docs/increments/2.2-admin-classification.md has the plan).
- Hierarchy import and export (`keel-classification/1`, JSON and CSV, [docs/migration/classification-format.md](../migration/classification-format.md)): classes and attributes are upserted by code and name; the import never deletes, moves or retires. A dry run executes the same code in a transaction and rolls back, so its report is exactly what an apply does; any error applies nothing.

### Configuration export and import
- One canonical JSON document (`keel-config/1`): format, SHA-256 of the canonical content (sorted keys, no whitespace), and the content (attributes, current lifecycle definitions, lists, numbering prefix and width, reason codes, active workflow templates, pins, the class hierarchy). No users, secrets, counters or object data. A file whose hash does not match is rejected.
- The import compares item by item (create / change / retire / restore / blocked) and applies through the same services as the UI, so validation, database guards and audit events are identical, followed by one `admin.config_import` summary event. It is idempotent and stops at the first error (not atomic across items; applied items no longer differ, so a re-run continues). Items missing from the file are left alone. A round trip test proves the target's export hash equals the source's.

### What is deliberately not here
- Attributes of documents and change objects (those objects store no attribute values yet): the service throws `NotSupportedException` naming Phase 2c.
- Editing the PR, ECR, ECN and CT lifecycles (process rules live in code and triggers; ADR-0019): the editor shows them read-only and the service throws `NotSupportedException` naming Phase 5.
- Changing change classes beyond their labels, and change number prefixes (database format checks).

## Consequences
- Configuration changes are auditable and reversible by publishing another version; nothing is edited in place except attribute and list rows, which carry before/after audit events.
- Old iterations never change: retiring, versioning and moving never rewrite frozen data.
- Administrators see configuration-safety counts (revisions per lifecycle state, stored attribute values, classified parts) that include parts they may not read. They are counts only; part numbers appear only for parts the administrator may read.
- Part and class attribute edits are validated when a part is next saved, not retroactively.
