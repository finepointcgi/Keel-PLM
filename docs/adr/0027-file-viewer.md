# ADR-0027: In-browser file viewer (3D, PDF, images)

**Status:** Accepted · 2026-10-28 · Builds on [ADR-0004](0004-abac-and-markings.md), [ADR-0014](0014-blazor-server-ui.md), [ADR-0015](0015-vault-object-storage.md)

## Context
Engineers should see their data: open a drawing, a CAD model or an image from a document page or a part page without downloading it. The data is export-controlled, so a viewer must not become a side door: it streams the bytes of a file to the browser, it needs scripts, WebAssembly and workers that the application's strict Content-Security-Policy forbids everywhere else, and it renders formats (STEP, PDF, SVG) that are themselves complex and sometimes hostile input. The product is air-gapped: nothing may come from a CDN or the internet at run time.

## Decision

### 1. Security model: viewing is downloading
1. **Authorization.** Viewing a file requires `PlmAction.Read` and then `PlmAction.Download` on the document's markings, evaluated by `AccessPolicy` in the documents module, exactly as `DownloadAsync` does. Read alone is not enough (VWR-2). Today both actions are granted by the same roles, so "may read but may not download" cannot occur; the Forbidden branch exists, and the day the policy distinguishes them the viewer follows without a change. A caller who may not read gets the same **not found** as for a missing object, on the page, the metadata route and the content route.
2. **Audit.** Every delivered view is audited as `document.view` with the file name, file id, SHA-256, size, iteration label, banner, viewer type (`pdf`, `model3d`, `image`), detected format and handling (`pdf-stamped` or `overlay`). Every denial is audited (`Denied`, with the policy reasons), as is every refusal after authorization (too large, no preview, a gate said no, a PDF that cannot be marked) and an integrity failure (`Failure`). The audit event for a delivery is written before the first byte is sent. Describing a file for the viewer page is not audited when it succeeds: the facts it shows are a subset of the document page, which is audited (`document.read`) under the same permission.
3. **Transport.** The viewer is reached with the session cookie only; no token appears in any URL. Responses carry `Cache-Control: no-store, max-age=0` and `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `Accept-Ranges: none` and `X-Keel-Markings` (percent-encoded banner), like the download route. The media type sent is the one the **server** derived from the content, never the stored client-supplied one. The content response is also sandboxed (`Content-Security-Policy: default-src 'none'; sandbox`), so an SVG or any other file opened directly instead of through an image element cannot run script.
4. **Integrity.** Content is read through the same verified vault path as downloads: size and SHA-256 are checked before anything is sent (the whole file is in memory first). A mismatch is audited, answers 500 "Stored file failed integrity verification", and nothing is delivered.
5. **Marked output.** PDFs go through the **same marking pipeline as downloads** (`PdfMarker`): the banner, notices and traceability line are stamped into every page, and the viewer shows that stamped PDF, so what is on screen equals what a download contains (same page geometry, same text). A PDF that cannot be stamped (encrypted, damaged, larger than `MaxPdfStampBytes`) is **refused, never shown unmarked**; the user is pointed to the marked download (which falls back to a marked ZIP). Range requests are not honoured (`Accept-Ranges: none`): verification and stamping need the whole file.
6. **3D models and images cannot be stamped in place.** The viewer draws the banner and the distribution statement as an overlay over the canvas or image (and the page itself carries the banner at top and bottom and the statement above the bottom banner, rendered by the server from the object's markings). The 3D viewer's screenshot function renders the view into an image **with** the banner, the statement and a traceability line (document, iteration, file, SHA-256 prefix, UTC time) in added bands, not overprinted. A watchdog (`banner-guard.js`) restores a removed or altered banner or overlay and hides the file until the page is reloaded.
7. **Residual risk, stated plainly.** The overlay is a handling aid, **not DRM**. A user who is allowed to download a file can obviously save it, and a user with developer tools can defeat any script that runs in their own browser (the watchdog catches accidents and casual removal, not a determined user). What the viewer guarantees is the server side: authorization, integrity, audit, marked PDFs, no caching, no unmarked PDF, and no new route by which a user without Download rights obtains bytes. 3D and image bytes are delivered as stored (a download delivers them in a ZIP with a marking cover sheet, A10); the delivered view is audited as `handling: overlay` so reviewers can see which files were shown without in-file markings.
8. **One place to refuse.** `ViewerService` is the single place that decides whether a file is shown: content support, size limit, then every registered `IFileViewGate` (Keel.Core). A future quarantine or "not yet scanned" check from the compliance work implements `IFileViewGate`, is registered in DI, and refuses before any byte is read (VWR-8).
9. **Limits.** Defaults: 100 MiB for 3D models, 50 MiB for PDFs, 50 MiB for images, a 5,000,000 triangle budget in the browser, and at most 8 files held in memory at once (others wait up to 15 s and get 503 `Retry-After`). All configurable under `Keel:Viewer`. Above the limit the page shows "too large to preview" with the limit and the (marked) download action.
10. **Type detection never trusts the name or the stored media type** (VWR-3). PDF, PNG, JPEG, GIF, WebP, GLB and STEP are recognised by signature; STL (binary: size formula; ASCII: keywords), OBJ, glTF JSON, SVG and IGES by a structural check **and** their extension. A name that disagrees with a signature is shown as what the content is, with a warning; a file whose content does not match its name gets no preview. The check runs on the head of the file for the page and again on the verified bytes before delivery.

### 2. Architecture
- **`Keel.Viewer`** (new library; references only Keel.Core, Keel.Security, Keel.Audit; namespace `Keel.Viewing`, because a namespace called `Keel.Viewer` shadows every identifier named `Viewer` in the other modules' code): detection (`FileSniffer`), limits (`ViewerOptions`), the single decision point (`ViewerService`) and the policies (`ViewerCsp`).
- **Cross-module behaviour goes through Keel.Core:** `IViewableFileSource` (+ `ViewableFile`, `ViewContent`, `FileFormats`, `IFileViewGate`) is implemented by `DocumentService` in a new file of Keel.Documents (`DocumentService.View.cs`). Access control, integrity, PDF marking and the audit events stay in the owning module.
- **Host:** `ViewerEndpoints` (Keel.Api) maps `/viewer/documents/{number}/files/{fileId}` (the page), `/viewer/documents/{number}/primary[?revision=]` (redirect to the primary file's page, for "open drawing" from part pages), `/viewer/meta/…` (JSON) and `/viewer/content/…` (bytes), all `RequireAuthorization(AnyPlmRole)` on the cookie scheme.
- **Page:** a **standalone HTML document**, not a Blazor page or route: `ViewerDocument.razor` is rendered to a string with `HtmlRenderer` (no circuit, no `blazor.web.js`), reached by full navigation (links carry `target="_top"` and `data-enhance-nav="false"`). It draws the marking banner at top and bottom from `ViewableFile.Banner` (= `Markings.BannerText()` of the object), the distribution statement, a "Back to document" link and the viewer canvas. An architecture test requires every viewer document to render both banners from the model, the statement and no inline script or style; another requires the host to take the banner from the described file.
- **Assets:** `src/Keel.Web/wwwroot/viewer/` (own ES modules and CSS) and `…/vendor/` (three.js bundle, occt-import-js JS and WASM, pdf.js and its worker), listed with SHA-256 in `manifest.json`. A unit test fails when any file changes without the manifest, and when a vendored file's hash and license are not in `docs/third-party/viewer.md`. A second test rejects external URLs, `eval`, `Function(`, `innerHTML` and inline-style APIs in the viewer's own files.

### 3. Content-Security-Policy (the global policy is unchanged)
Every route except the viewer's keeps `default-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'[ IdP]` (an integration test asserts the literal header on the API, the health routes, the download route, the application's own static files and a Blazor page, and a unit test asserts which paths get which policy). `ViewerCsp.ForPath` picks, in one place:

| Response | Policy | Differs from global |
|---|---|---|
| Viewer page, metadata, own scripts, CSS, vendored libraries | `default-src 'self'; worker-src 'self'; img-src 'self' data: blob:; connect-src 'self' data: blob:; object-src 'none'; frame-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action 'none'` | adds `worker-src 'self'` (workers from our origin only, never `blob:`), `img-src`/`connect-src` with `data:` and `blob:` (glTF textures and embedded buffers become `blob:`/`data:` URLs the page creates itself; they cannot load script and no network origin is named, so nothing can be sent anywhere), `object-src 'none'`, `frame-src 'none'`, and `form-action 'none'`. **`script-src` is not widened.** |
| `/viewer/content/…` (raw bytes) | `default-src 'none'; sandbox; frame-ancestors 'none'; …` | sandboxed, nothing loads |
| `step-worker.js` (CAD import worker) | `default-src 'none'; script-src 'self' 'unsafe-eval' 'wasm-unsafe-eval'; connect-src 'self'; …` | see below |
| `pdf.worker.min.mjs` | `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; …` | WASM for pdf.js's JPEG 2000 decoder |

**Finding while testing:** `'wasm-unsafe-eval'` alone is **not enough** for the OpenCascade importer. Its Embind layer builds call wrappers with the `Function` constructor, so the worker also needs `'unsafe-eval'`. Instead of granting that to the page, it is granted to the **worker script's own response** (a dedicated worker's policy is the one on its script's response), so the page, its DOM and its cookies-bearing JavaScript never get `'unsafe-eval'` or `'wasm-unsafe-eval'`. The worker has no DOM, may fetch only `'self'` (its `.wasm`), and is given only the file bytes by message. The wrapper source Embind evaluates is generated from the module's own type table, not from file content. An alternative that removes `'unsafe-eval'` altogether is rebuilding occt-import-js with Emscripten's `DYNAMIC_EXECUTION=0` (follow-up, VWR-12).

No inline script and no inline style exist on the viewer page; scripts set styles through the CSSOM (`element.style.x = …`), which the CSP allows. The viewer is never framed (`frame-ancestors 'none'`).

### 4. PDF: pdf.js, not the browser's built-in viewer (VWR-5)
The built-in viewers need `<iframe>`, `<embed>` or `<object>` (so `frame-src`/`object-src 'self'`), are plugins whose behaviour and PDF-JavaScript policy differ per browser, cannot be driven or tested the same way, and are blocked outright by the `sandbox` directive on the content response. pdf.js (Apache-2.0, 4.10.38, vendored) renders to canvas in a worker from our origin with `isEvalSupported: false` and `enableScripting: false`, so no JavaScript in a PDF ever runs; links and forms are inert; the text layer keeps text selectable; page navigation, zoom (buttons, wheel via the browser, keyboard `+ - 0 9`, Home/End, Page Up/Down), fit width / fit page, and an invert switch for low light are provided; the toolbar follows `forced-colors`. Not provided: annotations, form filling, search within the PDF (browser find works on the text layer of rendered pages).

### 5. 3D: three.js and OpenCascade WebAssembly, and what the licence means (VWR-12)
- **Rendering:** three.js 0.186.1 (MIT) with `OrbitControls`, `STLLoader`, `OBJLoader` and `GLTFLoader`, bundled with esbuild from a pinned `package-lock.json` (`tools/viewer-vendor`, maintainer-only, never run at run time). Tools: orbit/pan/zoom, fit, standard views, shaded/wireframe, bounding box dimensions, point-to-point measurement, one-axis section plane, exploded view for files with two or more top-level parts (STEP assemblies, glTF/OBJ nodes), screenshot with markings, triangle budget with a message, and GPU memory released on `pagehide`.
- **STEP and IGES:** occt-import-js 0.0.23 (OpenCascade Technology compiled to WebAssembly by the project with Emscripten 3.1.69), run in a Web Worker so the UI stays responsive. **Licence: LGPL-2.1** (the package ships the plain LGPL-2.1 text for both occt-import-js and OCCT; OCCT upstream adds the "Open CASCADE exception", which only loosens it, and we plan for the stricter text).
- **What LGPL-2.1 means for a product delivered to a defense contractor** (engineering reading, not legal advice; counsel should confirm):
  1. The library is **not combined into our code**: it is two unmodified files (`occt-import-js.js` glue and `occt-import-js.wasm`) loaded by a worker through `importScripts` and `WebAssembly`, talking to the rest of the viewer only by `postMessage`. Our own code stays under our own terms (a "work that uses the library", §5), so the copyleft does not reach Keel PLM.
  2. **Replaceability (§6):** a recipient must be able to replace the library with a modified version. They can: the files are separate, unmodified and unminified-further, in `wwwroot/viewer/vendor/`, loaded by relative URL. (`manifest.json` and its test are a *repository* integrity control; nothing at run time refuses a replaced file. A site that replaces the file updates the manifest the same way.)
  3. **Notices and source (§§1, 4, 6):** each delivery of the product must include the licence text (shipped in `docs/third-party/viewer-licenses/` and to be copied into the image and the offline bundle), the notices in `docs/third-party/viewer.md`, and either the corresponding source or a written offer valid for at least three years. For an air-gapped site "download it from GitHub" is not an offer the recipient can use: **release engineering must put the source archives (occt-import-js v0.0.23 and the OCCT revision pinned by its submodule, plus the Emscripten version and build script) into the offline bundle**. That is not done in this increment and is listed in the notes.
  4. LGPL imposes nothing on how the product is *used* inside the contractor, on classification of the data, or on export control of the data; the library is publicly available open-source software and contains no cryptography.
- **Alternatives considered:** (a) server-side conversion with OCCT or FreeCAD: the same licence applies, plus a native C++ stack and a second runtime on a FIPS-mode host, and each conversion is a heavy request; (b) a commercial converter: licence and air-gap/supply issues; (c) no STEP support: fails the goal. Chosen: client-side WASM, isolated in one worker and two files.
- **Opt-out:** `Keel:Viewer:EnableCadImport=false` makes STEP and IGES show "no preview" with the facts and the download action, and the importer files are never requested; a site whose counsel declines the LGPL component can also delete the two files and their manifest rows.

## Consequences
- A user sees drawings, models and images in the browser with the markings in view; the cost is one more route family that must stay in step with downloads. Authorization and audit are not duplicated: they live in `DocumentService`, next to download.
- The viewer's CSP is looser than the application's in a few documented directives; the global policy is untouched, and each difference is tested.
- Whole files are read into server memory (bounded by the limits and a concurrency cap) and into browser memory; very large models are refused with a clear message instead of being streamed.
- STEP/IGES conversion cost is paid in the user's browser; a 100 MiB STEP can take a long time and a lot of memory. The 100 MiB default is the product limit, not a promise of speed.

## Not in this increment
Thumbnails in lists (needs server-side rendering), exploded view by PLM BOM level (needs STEP assembly names matched to BOM find numbers), annotation and markup, PDF search, comparison of two revisions, DRACO/KTX2/meshopt compressed glTF (`NotSupportedException`-style message: "this glTF uses compression the viewer does not include"), external references of a `.gltf` (upload a `.glb`), PDF forms.
